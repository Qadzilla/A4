## How to use this document

Each **build unit (BU)** is one coding session's worth of work. They are ordered by dependency — you cannot start a unit until its listed inputs are complete. Within a session, follow this workflow:

1. Read the BU description top to bottom
2. Create/modify the listed files
3. Run the listed tests — all must pass before moving on
4. Run the verification checks
5. Mark the BU as done in the completion checklist at the bottom

**Format of each BU:**

- **Goal** — one sentence describing the outcome
- **Inputs** — which prior BUs must be done first (or "None")
- **Creates / Modifies** — exact file paths affected
- **Description** — what to build, decisions already made, edge cases, constraints
- **Tests** — full specs: file path, `describe`/`it` blocks, assertions, setup/teardown
- **Verification** — manual and automated checks to confirm the unit works

**No code in this document.** All code decisions happen in coding sessions. This doc tells you *what* to build and *how to know it's correct*, not *how to write it*.

## Phase 5 goal

The AI gains the ability to reason across workspace boundaries, remember past conversations, and model complex financial scenarios. Paige can answer "What's my total tax liability across personal + business?" by querying multiple workspaces, compare "max out 401k vs just the match" by producing side-by-side projection cards, and reference prior conversations with "Last month you asked about refinancing — rates have dropped since then." These capabilities are backed by conversation summaries stored in the DB, cross-workspace permission checks, scenario comparison tools, and guided reasoning prompts — all built on top of the existing 25-tool pipeline and proactive insights engine.

## BU-01 — `conversations.summary` column + shared schemas

**Goal:** Add a nullable `summary` text column to the existing `conversations` table and update the shared Zod schemas so conversation summaries can be persisted and validated.

**Inputs:** None (Phase 4 complete)

**Creates / Modifies:**
- `apps/server/src/db/schema.ts` — add `summary` column to `conversations` table
- `packages/shared-schemas/src/chat.ts` — add `summary` field to `conversationSchema` and `conversationListItemSchema`
- `apps/server/src/__tests__/conversations-summary.test.ts` — new test file

**Description:**

Add a single nullable `summary` text column to the `conversations` table in `schema.ts`. Place it after the `model` column, following the existing column pattern: `summary: text('summary')`. No default — it starts null and gets populated by the summarization engine (BU-02) after sufficient conversation history accumulates.

Update `packages/shared-schemas/src/chat.ts`:
- Add `summary: z.string().nullable().optional()` to `conversationSchema`
- Add `summary: z.string().nullable().optional()` to `conversationListItemSchema`

Decisions already made:
- **Column on `conversations`, not a new table.** The relationship is 1:1 — every conversation has at most one summary. A separate table would add join complexity for zero benefit.
- **Nullable text, not JSON.** Summaries are plain prose (1-3 sentences), not structured data. No need for JSON parsing overhead.
- **No max length constraint.** Summaries are generated by Haiku with a token budget (BU-02), so they're naturally bounded to ~200-300 characters. Adding a DB constraint would just create a failure mode with no benefit.
- **No index on `summary`.** We never query by summary content — only by `workspaceId + userId` which is already the access pattern.

Edge cases:
- Existing conversations have `summary = null` — this is correct. Summaries will be backfilled lazily as users chat (or never, for abandoned conversations).
- The `summary` column must be added with SQLite `ALTER TABLE ADD COLUMN` compatibility — nullable columns with no default are safe to add without migrating existing rows.

## BU-02 — Conversation summarization engine

**Goal:** Create a server-side service that generates concise conversation summaries using Claude Haiku, triggered after sufficient conversation history accumulates.

**Inputs:** BU-01

**Creates / Modifies:**
- `apps/server/src/services/conversation-summarizer.ts` — new file
- `apps/server/src/__tests__/conversation-summarizer.test.ts` — new test file

**Description:**

Create `conversation-summarizer.ts` with a single top-level export:

`summarizeConversation(db: DB, conversationId: string): Promise<void>`

This function:
1. Loads all messages for the conversation, ordered by `createdAt` ascending
2. Counts user messages — if fewer than 4 user messages, returns early (not enough substance to summarize)
3. Checks the conversation's existing `summary` and `updatedAt` — if a summary already exists and `updatedAt` is within the last 10 minutes, returns early (debounce)
4. Builds a summarization prompt containing the conversation messages (user + assistant only, tool messages excluded)
5. Calls Claude Haiku (`claude-haiku-4-5-20251001`) via the existing `Anthropic` SDK wrapper in `apps/server/src/services/anthropic.ts` with:
   - System prompt: "Summarize this financial conversation in 1-3 sentences. Focus on: what financial topics were discussed, what decisions were made, what data was referenced, and any action items. Be specific with numbers and dates. Do not include greetings or pleasantries."
   - Max tokens: 200
   - Temperature: 0 (deterministic)
6. Writes the summary to `conversations.summary` where `id = conversationId`
7. Updates `conversations.updatedAt` to now

**Error handling:** The entire function is wrapped in a try/catch. On any failure (API error, DB error, timeout), log the error and return silently. Summarization is non-blocking — a failed summary never impacts the user's chat experience.

**Cost model:** Haiku is the cheapest model ($0.25/MTok input, $1.25/MTok output). A typical conversation of 20 messages is ~2000 tokens input + 100 tokens output = ~$0.0006 per summary. At 100 summaries/day, that's $0.06/day.

Decisions already made:
- **Haiku, not Sonnet.** Summarization is a bulk operation, not latency-sensitive. Haiku produces adequate 1-3 sentence summaries at 12x lower cost than Sonnet.
- **4-message threshold.** Short conversations (1-3 user messages) don't need summaries — the messages themselves are short enough to include in context directly.
- **10-minute debounce.** Prevents re-summarizing during an active conversation. The summary is updated after the conversation goes quiet.
- **Fire-and-forget pattern.** The caller (BU-03's chat-stream integration) does not await the result. Summary generation happens asynchronously after the response is streamed.
- **No separate queue or job system.** The summarization is lightweight (single Haiku call) and infrequent (at most once per 10 minutes per conversation). A queue would be over-engineering.
- **Tool messages excluded from summarization prompt.** Tool call/result messages are verbose JSON that inflates token count without adding summarization value. The assistant's text responses already incorporate tool results in natural language.

Edge cases:
- Very long conversations (100+ messages): truncate the message list to the most recent 50 messages to stay within Haiku's context window. Older messages are less relevant for a summary of the conversation's current state.
- Concurrent summarization: if two summarization calls race for the same conversation, both will write a summary — the second write wins. This is acceptable because summaries are idempotent (both calls see the same messages).
- Empty assistant responses: skip messages with empty content.

## BU-03 — Session memory injection into system prompt

**Goal:** Inject summaries of recent conversations into the system prompt so Paige can reference prior sessions, and trigger summarization after each chat turn.

**Inputs:** BU-02

**Creates / Modifies:**
- `apps/server/src/services/ai-context.ts` — add `buildConversationMemorySection`
- `apps/server/src/routes/chat-stream.ts` — add fire-and-forget summarization trigger
- `apps/server/src/__tests__/ai-context.test.ts` — extend with conversation memory tests

**Description:**

**New section builder in `ai-context.ts`:**

Add `buildConversationMemorySection(db: DB, userId: string, workspaceId: string, currentConversationId: string): Promise<string>`

This function:
1. Queries `conversations` where `userId` matches, `workspaceId` matches, `summary IS NOT NULL`, and `id != currentConversationId` (exclude the current conversation)
2. Orders by `updatedAt` descending, limits to 5 results
3. Budgets total characters to 2000 — iterate through results, accumulating summaries, stop when budget is reached
4. If no summarized conversations found: return empty string (section omitted)
5. Format as a markdown section:

```
## Prior conversation context

You have discussed the following topics with this user in previous sessions. Reference these when relevant — do not repeat them verbatim, but use them to provide continuity:

- **{title}** ({relative time ago}): {summary}
- **{title}** ({relative time ago}): {summary}
...
```

Add `buildConversationMemorySection` to the `Promise.all` array in `buildWorkspaceContext`, alongside the existing section builders. Pass `currentConversationId` through from the chat stream route.

**Modify `buildWorkspaceContext` signature:** Add an optional `currentConversationId` parameter:

`buildWorkspaceContext(db: DB, userId: string, workspaceId: string, currentConversationId?: string): Promise<string>`

When `currentConversationId` is provided, include the conversation memory section. When omitted (e.g., for insight generation context), skip it. This keeps backward compatibility.

**Summarization trigger in `chat-stream.ts`:**

After the final `done` SSE event is sent (after the tool loop completes and the final response is streamed), trigger summarization as fire-and-forget:

1. Import `summarizeConversation` from `conversation-summarizer.ts`
2. After `sendSSE(res, { type: 'done', ... })`, call `summarizeConversation(db, conversationId)` — do NOT await it
3. The summarization runs asynchronously after the response stream closes

This means:
- Every chat turn potentially triggers a summarization check
- The debounce logic in `summarizeConversation` (BU-02) ensures it only actually runs if ≥4 user messages and the last summary is >10 minutes old
- The user never waits for summarization — it's invisible

**Update SYSTEM_PREAMBLE:**

Add to the existing preamble after the insights awareness line:

> "You have memory of prior conversations with this user via session summaries. When prior context is relevant (e.g., the user follows up on a topic from a previous session), reference it naturally. Say 'Last time we discussed X' or 'Following up on your question about Y'. Do not fabricate prior conversation history — only reference what appears in the Prior conversation context section."

Edge cases:
- First conversation in a workspace: no prior summaries exist → memory section is omitted entirely.
- All prior conversations have null summaries (too short): same as above — section omitted.
- Character budget reached mid-summary: truncate the last summary at a sentence boundary (find last period before budget), don't include partial sentences.
- `currentConversationId` is undefined (insight generation flow): skip the memory section entirely. This is correct — insights don't need conversation memory.

Decisions already made:
- **5 most recent conversations, 2000 char budget.** Keeps context injection under ~500 tokens. More would dilute the workspace data context that Paige needs for accurate answers.
- **Exclude current conversation.** The user's current messages are already in the message history — including the current conversation's summary would be redundant.
- **Fire-and-forget trigger, not a cron job.** Simpler, no infrastructure dependency, and naturally fires at the right cadence (after conversations).

## BU-04 — Cross-workspace permission model + tools

**Goal:** Add `list_workspaces` and `query_workspace` tools that let Paige access data from the user's other workspaces, with ownership verification.

**Inputs:** None (Phase 4 complete — can start in parallel with BU-01)

**Creates / Modifies:**
- `apps/server/src/services/cross-workspace.ts` — new file: permission check + dispatch
- `apps/server/src/services/ai-tools.ts` — add 2 new tool definitions + executors
- `apps/server/src/services/ai-context.ts` — update SYSTEM_PREAMBLE with cross-workspace guidance
- `apps/server/src/__tests__/cross-workspace.test.ts` — new test file

**Description:**

**New service: `cross-workspace.ts`**

Create `apps/server/src/services/cross-workspace.ts` with two exports:

1. `verifyWorkspaceAccess(db: DB, userId: string, targetWorkspaceId: string): Promise<boolean>`
   - Queries `workspaces` table where `id = targetWorkspaceId` and `userId` matches
   - Returns `true` if a row exists, `false` otherwise
   - This is the permission gate — users can only query workspaces they own

2. `dispatchWorkspaceQuery(db: DB, userId: string, targetWorkspaceId: string, question: string): Promise<string>`
   - Takes a natural-language question about a target workspace
   - Uses keyword matching to determine which existing tool executors to call:
     - Keywords `account`, `balance`, `cash` → execute `get_accounts` tool for target workspace
     - Keywords `budget`, `spending`, `expense` → execute `get_budgets` tool for target workspace
     - Keywords `networth`, `net worth`, `assets` → execute `get_networth` tool for target workspace
     - Keywords `subscription`, `recurring` → execute `get_subscriptions` tool for target workspace
     - Keywords `debt`, `loan`, `owe` → execute `get_debts` tool for target workspace
     - Keywords `holding`, `investment`, `portfolio`, `stock` → execute `get_holdings` tool for target workspace
     - Keywords `invoice` → execute `get_invoices` tool for target workspace
     - No keyword match → build a workspace summary context for the target workspace (reuse `buildWorkspaceContext` from `ai-context.ts` without the preamble)
   - Keyword matching is case-insensitive, checks for substring presence in the `question` string
   - Multiple keyword matches are allowed — run all matching tools and concatenate results
   - Returns a formatted string: "Data from workspace '{workspaceName}':\n\n{tool results}"

**New tool definitions in `ai-tools.ts`:**

Add two tools to the `getToolDefinitions()` array:

Tool 1: `list_workspaces`
- Description: "List all workspaces owned by the current user. Use this to discover what workspaces are available before querying across them."
- Input schema: empty object (no parameters)
- Executor: query `workspaces` where `userId` matches, return array of `{ id, name, type, description }` for each workspace

Tool 2: `query_workspace`
- Description: "Query financial data from a different workspace. The user must own the target workspace. Use list_workspaces first to discover available workspaces."
- Input schema: `{ workspace_id: string, question: string }`
- Executor:
  1. Call `verifyWorkspaceAccess` — if false, return error: "You don't have access to that workspace."
  2. Call `dispatchWorkspaceQuery` with the target workspace ID and question
  3. Return the formatted result string

**Update SYSTEM_PREAMBLE in `ai-context.ts`:**

Add after the tool usage guidelines section:

> "### Cross-workspace queries
> You can access data from the user's other workspaces using list_workspaces and query_workspace. Use these when the user asks about data across workspaces (e.g., 'total cash across all accounts', 'compare my personal and business expenses'). Always call list_workspaces first to discover available workspaces before querying. Never assume workspace IDs — always look them up."

Decisions already made:
- **Keyword dispatch, not a secondary Claude call.** Sending the question to another LLM call to decide which tool to run would be expensive ($0.003+ per cross-workspace query) and add 1-2 seconds latency. Keyword matching is deterministic, instant, and free. The keywords cover the 7 major data types that A4 tracks. For questions that don't match keywords, the full workspace summary provides a fallback.
- **No new DB tables.** Cross-workspace access is checked against the existing `workspaces` table. No audit log or access control table needed for MVP.
- **Ownership-only permission model.** Users can only query their own workspaces. Shared workspace access (team features) is a future concern.
- **Reuse existing tool executors.** The `safeExecuteTool` function in `ai-tools.ts` already handles tool execution with error wrapping. Cross-workspace dispatch creates a temporary `ToolContext` with the target workspace's ID and calls the same executors.

Edge cases:
- User has only 1 workspace: `list_workspaces` returns a single workspace. `query_workspace` still works (user can query their own workspace via this tool, though it's redundant). No special handling needed.
- Target workspace has no data: tools return empty results (e.g., "No accounts found"). The formatted response conveys this naturally.
- Invalid workspace ID: `verifyWorkspaceAccess` returns false → error message returned to Paige → Paige tells the user.
- Question matches no keywords: falls back to full workspace summary, which includes all data sections.
- Question matches multiple keywords: all matching tools run, results concatenated. This is correct — a question like "what's my cash and debt situation?" should return both accounts and debts.

## BU-07 — Scenario modeling tools

**Goal:** Add a `create_scenario_comparison` tool that generates multiple projection/calculator cards and arranges them side-by-side on the canvas for visual comparison.

**Inputs:** None (Phase 4 complete — can start in parallel with BU-01 and BU-04)

**Creates / Modifies:**
- `apps/server/src/services/scenario-engine.ts` — new file: scenario execution + canvas item creation
- `apps/server/src/services/ai-tools.ts` — add `create_scenario_comparison` tool definition + executor
- `apps/server/src/__tests__/scenario-engine.test.ts` — new test file

**Description:**

**New service: `scenario-engine.ts`**

Create `apps/server/src/services/scenario-engine.ts` with a single export:

`executeScenarioComparison(db: DB, context: ToolContext, scenarios: ScenarioInput[]): Promise<ScenarioResult>`

Where `ScenarioInput` is:
```
{
  name: string,           // e.g., "Max 401k" or "Match only"
  cardType: string,       // one of the calculator item types
  parameters: Record<string, unknown>,  // type-specific inputs
}
```

And `ScenarioResult` is:
```
{
  pageId: string,          // ID of the comparison page canvas item
  cardIds: string[],       // IDs of the created calculator cards
  summaries: string[],     // text summary of each scenario's key result
}
```

This function:
1. Validates that `scenarios` has 2-4 entries (minimum 2 for comparison, maximum 4 to fit on canvas)
2. For each scenario, creates a canvas item of the specified `cardType` with the given `parameters` as data
3. Uses the existing pure calculation functions from `apps/server/src/lib/calc.ts` to compute results:
   - `projection-card` → `computeProjection`
   - `loan-calculator-card` → `computeLoan`
   - `tax-estimator-card` → `computeTaxEstimate`
   - `breakeven-card` → `computeBreakeven`
   - `depreciation-card` → `computeDepreciation`
   - `rent-vs-buy-card` → `computeRentVsBuy`
4. Positions cards side-by-side with 40px horizontal gap, using `findNextPosition` from `apps/server/src/services/auto-position.ts` for the first card's position, then offsetting subsequent cards
5. Uses default dimensions from `apps/server/src/services/canvas-defaults.ts` (`ITEM_DEFAULTS`) for each card type
6. Creates an `a4-page` canvas item as a comparison summary page, positioned above the scenario cards:
   - Title: the comparison name (e.g., "401k: Max vs Match")
   - Content: a markdown table comparing key metrics across all scenarios
   - The comparison table columns are: Scenario Name + the key output metrics from the calculation
7. Inserts all canvas items in a single transaction via `db.insert(canvasItems).values([...])`
8. Generates a text summary for each scenario (1-2 sentences with key numbers) for Paige to include in the chat response

**New tool in `ai-tools.ts`:**

Tool: `create_scenario_comparison`
- Description: "Create and compare 2-4 financial scenarios side by side on the canvas. Each scenario creates a calculator card with specific parameters. A comparison page summarizes the differences. Use this for 'what if' questions like 'max out 401k vs just the match' or 'pay off car loan early vs invest the difference'."
- Input schema:
  ```
  {
    comparison_name: string,          // title for the comparison page
    scenarios: [
      {
        name: string,                // scenario label
        card_type: string,           // canvas item type (projection-card, loan-calculator-card, etc.)
        parameters: object,          // type-specific calculation inputs
      }
    ]  // min 2, max 4
  }
  ```
- Executor: validate inputs, call `executeScenarioComparison`, return the result with summaries

**Calculation parameter mapping:**

Paige constructs the `parameters` object based on the conversation. The tool definition includes descriptions of required parameters for each supported card type in the input schema description. The existing `createDefault*Data` functions in `calc.ts` provide the base shape — Paige overrides specific fields based on the user's scenario.

For example, "What if I pay off my car loan early (2 years) vs invest the difference?":
- Scenario 1: `{ name: "Pay off early", card_type: "loan-calculator-card", parameters: { principal: 20000, rate: 5.5, termMonths: 24 } }`
- Scenario 2: `{ name: "Invest difference", card_type: "projection-card", parameters: { initial: 0, monthly: 500, rate: 8, years: 5 } }`

**Canvas positioning:**

Cards are arranged in a horizontal row:
- First card: position from `findNextPosition(existingItems, cardWidth, cardHeight)`
- Second card: first card's x + cardWidth + 40
- Third card (if present): second card's x + cardWidth + 40
- Fourth card (if present): third card's x + cardWidth + 40
- Comparison page: centered above the card row, y = first card's y - pageHeight - 40

Decisions already made:
- **No new DB tables.** Scenarios reuse existing canvas item types. The comparison is just a page card with markdown content. There's no "scenario" entity in the DB.
- **Reuse existing calc functions.** The pure computation functions in `calc.ts` are already tested. The scenario engine is an orchestrator, not a calculator.
- **2-4 scenario limit.** More than 4 creates layout issues on the canvas. 2 is the minimum for a meaningful comparison.
- **Side-by-side horizontal layout.** Vertical stacking would require scrolling. Horizontal layout leverages the infinite canvas's width.
- **Comparison page is an `a4-page` item.** This is the existing rich-text page type. The markdown content is rendered by BlockNote's markdown importer.

Edge cases:
- Mixed card types in one comparison (e.g., loan vs projection): this is valid and common. Each card renders its own type. The comparison page extracts the key output metric from each card type.
- Invalid card type: return error "Unsupported card type: {type}. Supported types: projection-card, loan-calculator-card, tax-estimator-card, breakeven-card, depreciation-card, rent-vs-buy-card."
- Fewer than 2 scenarios: return error "Scenario comparison requires at least 2 scenarios."
- More than 4 scenarios: return error "Maximum 4 scenarios per comparison."
- Canvas is empty (no existing items): `findNextPosition` returns a default position. This works correctly.

**Description:**

**Add to SYSTEM_PREAMBLE in `ai-context.ts`:**

After the existing tool usage guidelines and cross-workspace guidance, add a new section:

```
## Complex analysis patterns

When the user asks a complex financial question, follow these structured reasoning approaches. Call tools in the order shown, then synthesize a recommendation.

### "Can I afford X?" pattern
1. get_accounts → check liquid cash for down payment/upfront costs
2. get_networth → assess overall financial health
3. Run the relevant calculator (calculate_loan for mortgages, calculate_projection for investments)
4. get_budgets → check monthly cash flow capacity against new obligations
5. Synthesize: state whether the user can afford it, quantify the margin, note risks

### "Compare options" pattern
1. list_workspaces → check if relevant data spans workspaces
2. Use create_scenario_comparison to build side-by-side cards
3. Highlight the key differentiators (total cost, monthly impact, timeline)
4. Make a recommendation with reasoning, not just numbers

### "Cross-workspace totals" pattern
1. list_workspaces → discover all workspaces
2. query_workspace for each relevant workspace
3. Aggregate the numbers yourself (sum, average, compare)
4. Present a unified view with per-workspace breakdown

### "Financial health check" pattern
1. get_accounts → liquid position
2. get_networth → net worth trend
3. get_budgets → spending vs. income
4. get_debts → debt-to-income ratio
5. get_holdings → investment allocation
6. Synthesize: traffic-light summary (green/yellow/red) for each area, overall score, top 3 action items
```

**This is prompt engineering only — no new code logic.** The tool loop already supports up to 10 rounds with 20 tools per round (implemented in Phase 2). The existing tool infrastructure handles multi-step execution. What's missing is the instructional guidance that tells Paige *how* to chain tools for common question types.

The reasoning patterns are templates, not strict rules. Paige uses judgment to skip irrelevant steps (e.g., if the user has no debts, skip the debt check in "Can I afford X?"). The patterns prevent Paige from giving a shallow answer when a thorough analysis is warranted.

Decisions already made:
- **Prompt engineering, not code.** The tool loop already works for multi-step execution. Adding more code would be over-engineering. The gap is instructional — Paige needs to know *which* tools to chain for *which* question types.
- **4 patterns cover the Phase 5 use cases.** "Can I afford X?" covers the mortgage/purchase scenario from the pipeline doc. "Compare options" covers scenario modeling. "Cross-workspace totals" covers the cross-workspace feature. "Financial health check" is a bonus that leverages all existing tools.
- **No chain-of-thought forcing.** Paige decides when to use these patterns based on question complexity. Simple questions ("What's my checking balance?") should still get short, direct answers.

Edge cases:
- User asks a question that doesn't match any pattern: Paige uses default behavior (answer from context or call individual tools). The patterns are additive, not restrictive.
- Paige tries to follow a pattern but a tool fails: the existing error handling in `safeExecuteTool` catches the error and returns it as a tool result. Paige should note what data is unavailable and still provide the best analysis possible with what it has.
- Very complex questions that need more than 10 tool rounds: this is unlikely with the patterns above (each pattern uses 4-6 tool calls). If it happens, the tool loop exits after round 10 and Paige synthesizes with whatever data it has. The `MAX_TOOL_ROUNDS = 10` limit in `chat-stream.ts` is sufficient.
